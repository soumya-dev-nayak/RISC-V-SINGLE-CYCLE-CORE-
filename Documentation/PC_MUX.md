# PC MUX (3:1) — Upgraded

## Overview
The **PC MUX** selects the next value to be loaded into the Program Counter (`PCNext`) from among three candidate sources: sequential execution (`PC+4`), a PC-relative branch/jump target (`PC+Imm`, used for branches and `JAL`), and a register-relative jump target (`JALR`, computed as `rs1 + imm` via the ALU). This module represents an **upgrade** from an earlier 2:1 mux design, expanding the selection logic to correctly support all RISC-V control-flow instruction types.

This module is **purely combinational**.

---

### The Bug Being Fixed
```verilog
// OLD (2:1) code:
assign PCNext = branch ? PCTarget : PCPlus4;
```
This older version only had two options: sequential (`PCPlus4`) or a branch target (`PCTarget`). The `Jump` control signal (generated elsewhere for `JAL`/`JALR`) was **never wired into the mux's selection logic** — meaning that even though the control unit correctly identified a `JAL`/`JALR` instruction and asserted `Jump`, the PC mux had no way to act on it. As a result, **`JAL` and `JALR` instructions failed to redirect the PC**, silently falling through to sequential execution instead of jumping — a critical functional bug in any datapath supporting unconditional jumps.

### The Fix
Replacing the single `branch` bit with a 2-bit `pc_sel` signal (presumably now derived from combined `Jump`/`Branch`/`ALU zero` logic upstream) allows the mux to distinguish between three next-PC sources explicitly, closing the gap that caused jumps to be silently dropped.

---

## Module Declaration

```verilog
module PC_MUX #(parameter N = 32)
(
    input  wire [1:0]   pc_sel,
    input  wire [N-1:0] PCPlus4,
    input  wire [N-1:0] PcTarget,
    input  wire [N-1:0] JalrTarget,
    output reg  [N-1:0] PCNext
);
```

## Parameters

| Parameter | Default | Description |
|-----------|---------|-------------|
| `N` | 32 | Address/data width, matching the processor's word size (RV32). |

## Ports

| Port | Direction | Width | Description |
|------|-----------|-------|--------------|
| `pc_sel` | Input | 2 bits | Select signal determining which candidate becomes the next PC. Generated by upstream control logic combining branch/jump/zero-flag decisions. |
| `PCPlus4` | Input | `N` bits | Sequential next-instruction address (`PC + 4`). |
| `PcTarget` | Input | `N` bits | PC-relative target address (`PC + Imm`) — used for taken branches **and** `JAL`. |
| `JalrTarget` | Input | `N` bits | Register-relative jump target for `JALR`, computed as `rs1 + I-type immediate` (typically produced by the main ALU, with the result's LSB cleared per the RISC-V spec, though that masking is not shown in this module). |
| `PCNext` | Output (reg) | `N` bits | Final selected next-PC value, fed back into the `PC` register module. |

---

## `pc_sel` Encoding

| `pc_sel` | Selected Value | Use Case |
|----------|------------------|----------|
| `2'b00` | `PCPlus4` | Default sequential execution — no branch/jump taken, or the instruction is not a control-flow instruction. |
| `2'b01` | `PcTarget` | Taken conditional branch (`BEQ`/`BNE`/`BLT`/etc. when condition holds), **or** `JAL` (which always "takes" its PC-relative target). |
| `2'b10` | `JalrTarget` | `JALR` — target computed via the ALU from a register base plus immediate offset. |
| `2'b11` (unused / default) | `PCPlus4` | Falls back to sequential execution as a safe default for the unused encoding. |

---

## Behavioral Logic

```verilog
always @(*) begin
    case (pc_sel)
        2'b00:   PCNext = PCPlus4;
        2'b01:   PCNext = PcTarget;
        2'b10:   PCNext = JalrTarget;
        default: PCNext = PCPlus4;
    endcase
end
```

- Combinational `always` block with a `case` statement on the 2-bit selector, directly implementing the 3:1 multiplexer.
- The `default` branch (covering `2'b11`) falls back to `PCPlus4`, which acts as a safe/defined behavior for the unused fourth encoding — preventing latch inference and providing deterministic behavior even for an invalid/unreachable select value.

---

## Design Notes & Observations

- **JAL and taken-branch share `PcTarget`**: Since both instruction types compute their target the same way (`PC + immediate`), they can safely share the same input port and `pc_sel` code (`2'b01`), simplifying the mux to 3 inputs instead of 4.
- **`pc_sel` generation is external**: This module does not compute `pc_sel` itself — it must be derived elsewhere (likely in the Main Control unit or a dedicated branch-decision block) by combining:
  - `Jump` (asserted for `JAL`)
  - `JumpReg`/similar (asserted for `JALR`)
  - `Branch` AND the ALU's `zero`/comparison result (asserted for a *taken* conditional branch)
  
  This external logic must correctly prioritize jumps over branches (or vice versa, depending on instruction encoding overlap) to generate the correct 2-bit `pc_sel` value.
- **`JalrTarget` LSB clearing**: Per the RISC-V specification, `JALR` targets must have their least-significant bit cleared (`target[0] = 0`) to enforce 2-byte alignment (or the ISA-specified alignment). This module assumes `JalrTarget` has already been correctly formed (with LSB cleared) by whatever computes it upstream (e.g., the ALU or a small correction adder) — no masking occurs within this mux itself.
- **Historical/documented bug fix**: The inline comments explicitly document the prior bug (missing `Jump` wiring) and its resolution, which is valuable for anyone tracing why the module evolved from 2:1 to 3:1 — a good practice for datapath debugging documentation.
- **Purely combinational, single-cycle friendly**: As with other datapath muxes in this design, no clocking is involved; the correct `PCNext` must be resolved entirely within the current cycle before the next active clock edge captures it into the `PC` register.

## Usage in the Datapath

```
                 ┌───────────┐
   PCPlus4 ─────►│           │
  PcTarget ─────►│  PC_MUX   │──── PCNext ────► PC register (next state)
JalrTarget ─────►│  (this)   │
                 └───────────┘
                       ▲
                       │
                    pc_sel  ◄─── derived from {Jump, JumpReg, Branch & ALU.zero}
```

This module is the final arbitration point in the fetch-stage control-flow logic, resolving which of the three possible "next instruction address" candidates actually gets latched into the `PC` register on the next clock edge — correctly supporting sequential execution, conditional branches, `JAL`, and `JALR` in a unified single-cycle datapath.
